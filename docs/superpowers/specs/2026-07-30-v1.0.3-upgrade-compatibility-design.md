# v1.0.3 Upgrade Compatibility Design

Status: Approved

## Problem

The published `v1.0.2` CLI validates the active release before performing an
upgrade. It added `runtime/rules/work-items.md` to the unconditional release
manifest, so a valid immutable `v1.0.1` installation fails validation because
that file did not exist until `v1.0.2`.

The failure occurs before the installation transaction. The active `v1.0.1`
record and checkout remain unchanged, but users cannot follow the supported
upgrade path.

## Chosen approach

Release `v1.0.3` with a version floor for the new runtime file:

- `runtime/rules/work-items.md` is optional only for `v1.0.0` and `v1.0.1`;
- it is required for `v1.0.2` and every later version;
- every other release-integrity check remains unchanged.

The validator will reuse the existing SemVer comparison instead of adding a
new parser or manifest abstraction.

## Rejected approaches

- Making the file optional for every release would allow a corrupted `v1.0.2`
  or later checkout to pass validation.
- Copying the file into an installed `v1.0.1` checkout would mutate an
  immutable release and then fail the clean-checkout integrity gate.
- Uninstalling before every upgrade would discard supported transactional
  upgrade behavior and client enrollment state.

## Upgrade flow

1. The `v1.0.3` launcher verifies its annotated tag and merge commit.
2. `cmd_install` loads the active `v1.0.1` release.
3. Release validation applies the historical manifest and accepts the absence
   of `runtime/rules/work-items.md`.
4. The existing transition gate confirms `v1.0.3` is a newer same-major
   release and that `--upgrade` was supplied.
5. The existing transaction installs and activates `v1.0.3`.
6. Normal instruction and connector setup resumes.

No application-repository file is created or changed.

## Failure behavior

- A `v1.0.2+` checkout missing `runtime/rules/work-items.md` still returns
  `GOVERNANCE_NOT_READY`.
- An invalid origin, tag, commit, catalog, schema, required legacy file, or
  dirty checkout still fails through the existing gates.
- Any failure before transaction commit leaves the active release unchanged.

## Verification

An integration regression will construct actual annotated `v1.0.1` and
`v1.0.3` release fixtures, remove `runtime/rules/work-items.md` only from the
historical fixture, and execute the real upgrade command.

The test must:

- fail against the `v1.0.2` validator with the reported missing-file error;
- pass after the version-floor change and activate the exact `v1.0.3` commit;
- prove a `v1.0.2+` fixture missing the file is still rejected;
- preserve the application repository and existing transactional checks.

The complete shell suite and release readiness checks must remain green.

## Release scope

- Bump the supported capability release and user-facing upgrade command to
  `v1.0.3`.
- Publish only after the exact reviewed merge is explicitly approved for
  release.
- Do not alter the existing `v1.0.1` or `v1.0.2` tags/releases.
